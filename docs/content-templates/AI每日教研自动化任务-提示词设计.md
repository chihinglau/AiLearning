# AI 每日教研自动化任务 · 提示词设计方案

面向 AiLearning 学科知识库：让大模型以「深圳地区资深优秀教师 + 学科教研员」身份，每天按年级/教材推进，向 `docs/content-templates` 增量产出符合导入规范的 JSON（知识点 + 题库），持续提升学生的知识掌握度与应试能力。

> 本版口径：**每日任务只产出 JSON 文件，不执行 README 里的导入/`--dry-run`，不连数据库、不跑 alembic 迁移。** 入库由人工或另行安排的流程负责。质量门改由不连库的本地自检脚本 `_validate_daily.py` 承担。
>
> 已按 2026-11-07 最新 `README.md`（新增深圳教材版本基线、来源与版权登记，高中教材矩阵已校正）、9 份学科模板、`backend/app/services/content_import.py` 重新评估。
>
> **本版状态（2026-11-07 晚，已核验）**：产出目标库定为 `ailearning_dev.db`（默认库，`DATABASE_URL` 未设置时即命中它）。dev 与 device 两库均已重建到 head `x1y2z3a4b5c6`，教材 / 章节 / 知识点 / 题目均为 146 / 126 / 337 / 646，重复教材 0，版本名一致，所以第二节的 `version` 表对两库通用，写哪边都不会挂错版本。README 的语文声明也已修正为 `人教版`。
>
> **⚠ 目录已重构（2026-11-07 晚，读本文档前先看这条）**：内容目录由扁平堆叠改为**按学科+年级分层**——`templates\`（9 份学科模板）、`baseline\`（知识点/章节基线）、`daily\{subject}\g{grade}\`（当日产出）、`ledger\{subject}\g{grade}.md`（台账）、`logs\{subject}_{semester}.md`（运行日志）。本文档前段（第一节至第六节）的「方案一/二/三」示例里出现的扁平文件名（如 `math_g8_first_*.json`、`_daily-ledger_*`、`_daily-run-log_*`）**只作演进记录**，现行路径统一以**第十节「目录结构」**与 `_daily-task-instruction.md` 的「固定配置 / 目录约定」为准；9 条定时任务的 query 已同步改写，不再引用旧路径。

## 使用方式（三步）

1. 填好下方**参数表**（含目标库，替换提示词里的 `{{ }}` 占位）。
2. 把**提示词 A** 发给助手 → 由助手创建「每日定时任务」（本地运行，要读写 `D:\` 路径）。
3. 定时任务每次都执行**提示词 B**（或长度受限时用**提示词 C 精简版**），产出当日文件并自检。
4. 若要一次排满整个学段（多年级 × 上下册），用**提示词 A2 批量布署**（见第三节之二），不要重复发 16 次提示词 A。

> 关键前提：定时任务触发时是**全新会话**，看不到现在的对话。学科、年级、教材、目录、产出量这些参数必须完整写进任务正文（提示词 B），不能依赖"上次说过"。

## 三之二、提示词 A2：批量布署（年级 × 学期矩阵）

> 用途：一次建 N 个「年级 × 学期」的每日任务。以数学 1-8 年级 × 上下册为例，就是 16 个独立任务。与提示词 A 的差别只有三点：参数是矩阵、时间必须错峰、验收先试点一个再放开。

### 批量前必须先核的三件事（2026-11-07 实测）

| 项 | 结论 | 影响 |
|---|---|---|
| 教材记录 | 数学 1-8 年级 × 上下册共 16 条，全部 `北师大版` | 可排，不会新建空教材 |
| 章节记录 | 1-3 年级已有简化章名（如 `10以内加减法`、`周长`）；**4-8 年级上册各只有 1 条占位章节 `样章·数与式·运算基础`** | 4-8 必须按教材真实目录新建章节，**不得沿用"样章"、也不得把知识点挂到它下面**；章名不带"第X章"前缀，写法写进台账后不再改（详见指令文件附录） |
| 产量 | 单任务 3-6 知识点 / 18-28 题；16 个全跑 = 每天 48-96 知识点、288-448 题 | 建议核心年级（6-8）满量，1-5 减半或减到 2-3 知识点 / 10-14 题 |

另外两点必须接受：① 16 个任务是 16 次独立会话，token 消耗与 16 个单任务之和相当；② 上下册同时开跑等于「提前学下册」，内容会超出当前教学进度。


### 批量任务的日常维护

| 场景 | 做法 |
|---|---|
| 某年级要暂停 | 停用该条任务，其余不受影响；台账保留，恢复后接着上次进度 |
| 进度太快/太慢 | 调该条任务正文里的"每日推进量"，不要改其他任务 |
| 章节名发现写错 | 只改台账里登记的写法，历史文件不动；次日按新写法，导入时会当作新章节 |
| 学期切换（上册→下册） | 不要复用同一条任务改参数：新建下册任务，上册任务停用，避免台账口径混乱 |

### 套餐任务上限（实测：10 条）与压缩方案

账号当前套餐**最多 10 个定时任务**（建第 11 条时被拒）。数学 1-8 年级 × 上下册 = 16 条超过上限，所以批量必须压缩。

| 方案 | 任务数 | 覆盖 | 每日产量 | 说明 |
|---|---|---|---|---|

### 跨日与批次日期（三班制必写的一条规则）

三班分别是 02:00 / 12:00 / 22:00，其中 22:00 那班有可能写到 00:30。跨零点的错法只有三种，规则逐一封住：

| 错法 | 后果 | 规则 |
|---|---|---|
| 文件名跟着系统日期走 | 同一批年级一半 `_20261107`、一半 `_20261108`，次日班把做过的当没做 | **批次日期 = 触发时刻的日期**，定下后全程不变；文件名、台账、日志都用它 |
| 次日班按"今天有没有跑过"判断 | 昨晚做过 5 个年级被当成没做，重做一遍 | 只看**新批次日期**的文件是否存在；旧日期文件不算也不重写 |
| 晚班硬撑跨零点 | 半成品、日期错乱、和次日首跑撞车 | **22:00 班最迟 23:30 停手**，没轮到的年级在运行日志写"顺延至次日首跑" |

配套两条：① 跨零点完成的年级，日志备注"跨零点完成 HH:MM"，方便事后核对；② 不搞"补昨天"——昨天缺的年级不在今天补，今天按台账"下一节计划"正常推进，缺的是数量不是进度。

### 多年级顺序模式的六条硬规则（已写进指令文件与任务 query）

1. 顺序 1→8；开工先读运行日志，当天未完成的年级优先补齐。
2. 一个年级走完全流程（含自检 0 错误）才进入下一个，不攒批校验。
3. 该年级今天已有同名文件 → 跳过并汇报，不重写、不加 `_r2`。
4. 时间/上下文不足 → 立即停手，运行日志记明还剩哪些年级，不留半成品。
5. 汇报给一张年级表（文件 / 知识点 / 题目 / 自检），合计与失败项单列。
6. 一天三次触发（02:00 首跑、12:00 中班、22:00 晚班）：后两班只补未完成的年级；某班进来发现 8 个年级都已完成，就只记一行"本轮已完成，无待办"。判断标准是"产出文件日期是否为今天"，不是"今天跑了几次"。
7. 三班之间用锁文件 `_daily-lock_math_first.txt` 互斥：锁存在且开始时间 <30 分钟 → 后来的直接跳过；>30 分钟视为残留锁，清掉再跑；执行结束必须删锁。

## 十、知识点重名防护机制（2026-11-07 补齐，解决"每天重复新建同名知识点"）

> **2026-11-07 已执行全量去重**：迁移 `y1z2a3b4c5d6` 保留 54 个 section 原名，重命名 56 个 point 为「名称（要点）」，题目外键不变，两库歧义均为 0；导入器与 seed 遇到重名 point 也会自动加后缀。基线已重建。下方“待决策”保留为历史记录。

### 问题

定时任务不连数据库，看不到库内已有的 337 个知识点节点，于是每天按自己的命名习惯新建知识点，几天后库里就堆出同名节点。后果不是"多几条"这么轻：

- 受影响的是**"按名称引用库内已有节点"这一条路径**，不是全流程卡死：导入器挂题时优先用同文件内声明的本地映射（`point_map` / `section_map`），文件里既声明 section 又声明 point 的，不会去查库、也不会被拒绝。只有题目引用"库内已有节点"时，同名节点 ≥2 才会抛「在库中有多个同名节点」（`content_import.py` 第 335-345 行）。
- 新建同名 point 不报错，但会**静默改写或偷偷改名**（第 267-298 行）：同一 section 下同名 → 复用该节点、覆盖讲解与来源；其他 section 下同名 → 自动改名成「名称（要点）」并新建。前者冲掉旧内容，后者在库里堆语义重复。

### 三个互相冲突的约束与解法

| 约束 | 单靠哪一件都不行 | 解法 |
|---|---|---|
| 静态基线会漂移（每天新增的不在里面） | 基线每天重生成？任务不能连库 | **台账补增量**：当天新增的 point 名逐条写进台账，"已用过 = 基线 ∪ 本任务台账" |
| 19 KB 基线整份读太贵 | 每个年级多花 ≈5k tokens | **分段读**：指令只要求读本学科本年级那几行（Read 的 offset/limit），其余不读 |
| 自检脚本是纯标准库、查不了库 | 只能靠人眼比对，必错 | **脚本读基线 JSON**：`--kp-baseline` 参数，重名/悬空/歧义一律判错误、退出码 1 |

### 交付的四件东西

| 文件 | 作用 | 谁读 |
|---|---|---|
| `baseline\_knowledge-points-baseline_20261107.md` | 人读版，按学科年级分段，每条标 ✅ 可引用 / ❌ 歧义 | 任务在第 3.6 步只读本学科本年级段 |
| `baseline\_knowledge-points-baseline_20261107.json` | 机读版，`subject → grade → 名称 → 出现次数` | `_validate_daily.py --kp-baseline` |
| `_validate_daily.py`（新增重名检查） | 裁判：文件里新建的 point 与库内重名、题目挂载点库内不存在、挂到歧义名，全部报错 | 每份 JSON 落盘后必跑 |
| `_daily-task-instruction.md`（新增第 3.6 步与 3.1 条） | 把"能不能用这个名字"写成可执行规则 | 9 条任务共用 |

判定口径（与导入源码逐条对齐）：

- 新建 point 名在库内出现 1 次 → 错误（同 section 会覆盖旧节点、其他 section 会被自动改名成「…（要点）」造出语义重复）；
- 新建 point 名在库内出现 ≥2 次 → 错误（歧义，按名称引用必失败）；
- 名称带「（要点」后缀 → 提醒（疑似从库内既有节点抄来，确认是否真新增）；
- 题目挂载点既不在本文件、库内也没有 → 错误；
- 题目挂载点库内出现 ≥2 次 → 错误（导入必拒）；
- 题目挂载点库内唯一 → 提醒（可导入）；
- **section 沿用同名不算重名**：导入按 `node_type=section` 过滤匹配，同名 point 不参与，重新声明是每天的必需动作。

**② 范围拦截（脚本级，不靠模型自觉）**

`_validate_daily.py --outline …` 解析大纲 md 的表格行，把本年级允许的单元名与节名收成白名单（三列表取第 2 列、两列表取第 1 列，节名按 `/` 拆开一并收），遇到文件里的 section 不在白名单直接判**错误**：

```text
[错误] 章节「复变函数论」不在本册教材大纲内（本册共 13 个允许的单元/小节，详见 baseline 下的大纲 md）；跑出教材范围会破坏教材完整性
```

- 大纲文件**自动发现**（`baseline\_outline_*_latest.md`），任务 query 不必带 `--outline`；
- 大纲按学科分文件（文件名里的学科代码决定只拦本学科），数学大纲不会误拦语文/物理；
- 已入库历史文件与学科模板降级为**提醒**（它们是旧口径产物，不该每天阻断复核）；**新产出一律判错误**。
- 反例测试已做：八年级改成「大学微积分入门」、六年级改成「复变函数论」都被拦住，改回来恢复通过。

**③ 版权红线（写进指令第一步与第三步）**

- 单元名、节标题可以写（事实性短标题）；**课文、例题、习题、插图一律不抄**，也不做"改几个数字"的伪原创。
- 所有知识点 `source_name="教研组自编"`、`source_type=original`；题目 `source_name="自主命题"`。
- 教材完整性靠"大纲覆盖全 + 知识点清单按单元铺满"来保证，不靠抄课本保证。

### 答案正确性（机检三件套，2026-11-07 落地）

| 手段 | 判什么 | 判定 |
|---|---|---|
| 算式求值 | 解析里每个含运算符的等式，左边用 ast 安全求值后与右边比对 | 偏差超容差 → **错误** |
| 舍入容差 | 等号右边的小数位数决定容差（`0.5 × 10^-位数`） | `1÷3=0.333`、`2.7÷1.1=2.4545` 属合法四舍五入，不判错 |
| 反面示例豁免 | 等式所在分句含「不对/不正确/错误/弄反/不能」时跳过 | 「8+3=5 把总数弄反了」不判错 |
| 选项闭合 | `multiple` 的解析必须逐项写出每个选项字号与该项结果 | 缺任一选项 → **错误**（模板与已入库文件降级提醒） |
| 数值型填空 | 答案是纯数字但解析里没有可求值算式 | **提醒**（机检无法验算，人工复核） |
| 已入库豁免 | manifest 里该路径 `status=ok` 且 sha256 一致 | 重名/多选闭合降级提醒，避免"文件查自己"的误报 |

实测价值：全目录复跑 8/8 通过后，仍靠机检抓出 `156×4` 的解析错步骤（写成「1×4=1，加 2 得 3」，正确是「1×4=4，加 2 得 6」）——说明**结构自检全过、答案却算错**是真实存在的，必须有机检兜底。

判重口径补充：manifest 里同一路径**曾经**成功入库过的文件，其知识点重名一律降级提醒（这些名字本来就是它自己入库时写进去的，不构成真新增冲突）；文件被改过（sha 变化）后，只有重名降级，多选闭合与算式仍按错误判——改过的内容必须重新过机检。

### 知识点上限与饱和后的处理

- **库侧没有上限**：`knowledge_points` 无 `UniqueConstraint`、无条数约束；导入器不校验知识点条数；README 只有「单文件建议 ≤200 题」的软约束。
- **真实上限由教材决定**：一册约 100-150 个知识点，45 个「年级×学期」约 9000-13500 个；题库按每点 ≥4 题算，上限约 3.6-5.4 万道。
- 到达上限不是"停下"，而是按**四阶段**继续：
  1. **覆盖**：一册的知识点全部走一遍（当前阶段）；
  2. **加深**：同知识点提难度（1-2 档 → 3-4 档）、换情境、加跨章综合；
  3. **应试**：按深圳中考/期末题型与分值分布做专题，题干独立可答；
  4. **饱和冻结**：第 2、3 轮都做完仍无可新增时，按「零新增处理」——台账记一行「YYYY-MM-DD 无新增：原因」，**不产出空 JSON、不靠改一两个字凑数**。
- 判断"已饱和"的依据只有台账与大纲覆盖率，不看模型感觉。

### 维护节奏

- 基线**只在库内容真的变了之后**才重生成（手工导入、批量导入完成时）。任务每天产出的 JSON 没入库，不该进基线。
- 用官方脚本生成，不要手写：`cd backend` 后
  `.venv\Scripts\python.exe -m scripts.build_kp_baseline --output-dir ..\docs\content-templates\baseline`
  它只读查库、同名时同时产出 `.json`（带 `_meta.ambiguous`）与 `.md`，**歧义 > 0 时退出码 1**，正好当入库后的门禁：门禁不过就别开下一轮自动化。
- 章节基线同样由脚本重建（不要手写）：
  `.venv\Scripts\python.exe -m scripts.build_chapters_baseline --output-dir ..\docs\content-templates\baseline`
- 两个脚本都会同时写带日期的归档文件和固定名 `_latest`，**任务与自检只读 `_latest`**；不要在任何提示词里写死日期，否则次日会读到旧快照。
- `_meta.ambiguous` 必须为 0；一旦非 0，说明库里又长出同名节点，先修数据再跑任务（任务侧无法自愈，只会继续被拒）。

### 入库五步（独立人工/受控环节，不属自动化）

自动化只写 JSON；入库单独做，五步固定顺序：

```powershell
cd backend

# 0) 备份目标库（建议；默认写 backend\build\backups）
.venv\Scripts\python.exe -m scripts.db_backup

# 1) 离线自检（不连库）：字段、版本名、题型、来源、重名。整棵 daily 树一次校验也行
.venv\Scripts\python.exe ..\docs\content-templates\_validate_daily.py `
  ..\docs\content-templates\daily --kp-baseline ..\docs\content-templates\baseline\_knowledge-points-baseline_latest.json

# 2) 预演：只扫 daily 树下当日文件（脚本递归扫描，子目录不影响匹配）
.venv\Scripts\python.exe -m scripts.import_content --path ..\docs\content-templates\daily --pattern "*_20261107.json" --dry-run

# 3) 正式导入：逐文件独立事务，写 hash 清单（同文件二次运行自动跳过）
.venv\Scripts\python.exe -m scripts.import_content --path ..\docs\content-templates\daily --pattern "*_20261107.json" --manifest ..\docs\content-templates\_import-manifest.json

# 4) 重建两份基线（名称唯一性门禁，歧义 > 0 返回码 1）；产物落 baseline 目录
.venv\Scripts\python.exe -m scripts.build_kp_baseline --output-dir ..\docs\content-templates\baseline
.venv\Scripts\python.exe -m scripts.build_chapters_baseline --output-dir ..\docs\content-templates\baseline
```

| 设计点 | 为什么这么定 |
|---|---|
| `--manifest` 记 sha256 + 目标库 | 幂等：内容没变且上次成功 → 跳过；失败记 `failed`，下次自动重试；换库或重建库时旧记录自动作废，避免"清单说导过、库里其实没有" |
| `--pattern` 只命中当日文件 | 隔离：不会把整目录 9 份模板再扫一遍；逐文件独立事务，单个坏文件不连坐 |
| 基线门禁前置 | 名称唯一性是"按名引用"的前提，歧义不清零，后面的产出注定被拒 |
| 基线读 `_latest` | 日期命名的快照只是归档；写死日期会在次日读到旧状态，重名判定失效 |
| 命名规范 | section 用教材真实章名、point 用知识点名；模板里仍写原名，撞名由导入器加「（要点）」兜底，题目挂载不受影响 |

### 怎么查、怎么算（官方口径）

豆包**不向模型暴露个人账户数据**，只能自己看：客户端「设置 → 豆包订阅 → 订阅与额度管理」，页面以**比例/数值**显示额度消耗，不显示 token。判断方法：

1. 记录今天的已用数值（P0）；
2. 连续跑 3 天，再看数值（P1），日增 = (P1 - P0) / 3；
3. 剩余可用天数 ≈ 剩余额度 / 日增。

另需注意：订阅用户还有 **5 小时 / 7 天滚动用量上限**，9 条任务同点触发（02:00 九条一起跑）最容易撞上 5 小时上限，表现为部分任务排队或失败——这也是 C 方案更稳的原因。
