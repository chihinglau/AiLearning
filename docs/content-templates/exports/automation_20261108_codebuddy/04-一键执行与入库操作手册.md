### 1.1 把当天的分片归集成整册（生成之后、导入之前，必做）

会话按「一节一批次」落盘时会产生 `_r2`/`_r3`… 分片，**分片永远进不了 manifest**
（`import` 只扫 `*_<batch>.json`，分片名末段是 `_rN`）。所以中间必须有「归集」这一步，
否则 `daily` 里明明有题、库里却 0 题——11-09 复核发现的 54 个空章就是这么来的。

```powershell
# ① 只出方案（只读，不改任何文件）：看哪册缺章、哪章多版本、分片归到哪
& $Py "$Root\docs\content-templates\_consolidate_daily.py" `
  --subjects math,chinese --grades 1-9 `
  --out "$Root\docs\content-templates\exports\review_20261109\consolidation-plan_<日期>.json" `
  --md  "$Root\docs\content-templates\exports\review_20261109\consolidation-plan_<日期>.md"

# ② 真写整册文件（落到 daily_consolidated\<subject>\g<N>\<subject>_g<N>_first_<日期>_book.json）
& $Py "$Root\docs\content-templates\_consolidate_daily.py" `
  --subjects math,chinese --grades 1-9 --apply
```

- `--subjects` / `--grades` 可任意组合（`--grades 1-9`、`1,8`、`3`）；**不传这两个参数**时按历史默认 12 册（g1+g8 上册）跑，行为与改造前完全一致。
- `--semester first|second`：只收该学期的 daily 文件，防止上册整册混进下册内容；默认 `first`。
- `--stamp YYYYMMDD`：整册文件名里的批次日期，默认今天；同一天重跑覆盖同名文件，不产 `_r2`。
- `--out-dir`：整册输出目录，默认 `docs\content-templates\daily_consolidated`。
- 裁定规则固定为 **非 legacy > 批次日期最新 > 题量最多 > mtime 最新**；分片不改名不删除，越界章节不并入，库内已存在的知识点不重复声明，空节剔除。
- **隔离名单（2026-11-10 评审复评 §八-1）**：`tasks.json` 的 `policy.quarantine_books.pairs` 登记了 34 册不合格整册（`subject:grade`）。归集器每次运行都读它，命中的册 `--apply` 时**跳过不写**，不会再生成可被 `*_book.json` 扫到的文件，因此「分片还在 → 重新归集 → 坏册复发」这条路已被堵住；方案表格多一列「隔离」，控制台打印「本次命中 N 册」。确需复核隔离件时加 `--force-quarantined`，输出名改为 `*_book.quarantined.json`。重跑合格并过 §3.8.7 闸门后，由人工从名单移除该册才恢复正式输出。

### 2.0.1 manifest 三列语义与「已入库」三态（第十一轮整改）

`_import-manifest.json` 的每条记录有三个哈希列，**含义不能混**：

| 列 | 含义 | 谁能改 |
|---|---|---|
| `imported_sha256` | **导入当刻**的字节 sha | **永不改写** |
| `current_file_sha256` | 盘上现值 | 每次入库更新 |
| `imported_content_sha256` | 导入当刻**剔除元数据键**（`_legacy` / `_legacy_note`）后的内容哈希 | 每次入库更新 |

校验器（`docs/content-templates/_validate_daily.py::_manifest_import_state`）据此判三态：

| 状态 | 条件 | 输出 | 影响 |
|---|---|---|---|
| `unchanged` | 字节与导入当刻一致 | `[已入库] 与 manifest 的 imported_sha256 一致……` | 重名/多选闭合按**提醒**（不阻断） |
| `meta_only` | 字节不同、**内容**哈希一致（只补了 `_legacy` 标记这类元数据） | `[已入库·仅元数据变更] 字节与导入当刻不同，但剔除元数据键后内容一致……` | 仍按已入库口径（不阻断） |
| `changed` | 字节与内容都不同 | `[文件已变更·未重导] 内容与导入当刻不同……` | 按新版本**从严**（重名报错） |

> 为什么要拆列：第十轮给 8 份 11-07 math JSON 打 `_legacy` 标记时，为了不让校验器假红，
> 把 manifest 里这 8 条的 `sha256` **就地刷成了当前文件版本**——于是 manifest 记的从
> 「导入当刻那一版」变成了「盘上现值」，**「已入库」的判据被降级成「这个文件被登记过」**：
> 任何对内容的就地改写，只要顺手刷 sha，校验器仍会说「已入库」。拆成三列 + 内容哈希后，
> 「刷 sha 就能骗过校验」这条路被堵死：内容变了就是 `changed`，从严检查。
> 迁移留痕：`_archive/_import-manifest.pre-3col.json`（逐字节副本）+
> `_archive/_import-manifest.pre-3col.provenance.txt`（49 条逐条明细：41 条 unchanged / 8 条 legacy_meta_only）。

### 3.1 库变更留痕（每次改库都要做，只读命令）

**配套规则二：改历史内容文件前先存副本。** 整库备份能还原数据库，还原不了 `daily\**\*.json`（`daily\` 在 git 里是 untracked）。所以凡是就地改已入库的 JSON（改 section 名、改点名、补题），先复制到：

```text
docs\content-templates\_archive\<文件名>.pre-<变更名>.json
```

并附一份同名 `.provenance.txt`（改了什么、怎么改、sha256）。示例：`_archive/english_g1_first_20261107.pre-remap.json`（第七轮 remap 之前，sha256 与 manifest 里的导入期 sha 一致，可当原件用）、`_archive/english_g1_first_20261107.pre-q4-add.json`（补第 4 题之前）。

> 小坑：这些 JSON 是 **CRLF** 换行。用 Python 文本模式读进来再写出去会把 sha 算错、还会把整个文件的行尾改掉；做「逆操作还原」时请按 bytes 处理（`read_bytes()` / `write_bytes()`），否则永远对不上 manifest 的 sha。

`audit` 支持 `--current <db>` 指定目标库（例如只对比两个备份之间的差异：`--since A.db --current B.db`），默认对比当前 `settings.database_url` 指向的库。

#### 3.1.1 `db_op_*.json` 统一骨架与历史字段映射（第十二轮整改）

**统一骨架（新脚本一律按这套输出）**：

```json
{
  "_meta": { "kind", "generated", "tool", "database", "backup", "semantics", "plan" },
  "stats": { "before", "after", "delta", ... },
```

#### 3.1.2 写盘前比字节（第十二轮整改）

`mtime` 是这套体系里「这个文件何时被动过」的唯一证据。**任何脚本写盘前先比字节，一致就不落盘**：

- `migrate_manifest_3col.py`：manifest 已是 schema v3 且三列一致 → 打印「[幂等] … 本次不落盘、不改 mtime」直接返回（实测复跑后 manifest mtime 仍是 `22:03:22`）。
- `mark_legacy_json.py`：本次零变更时不写 manifest、**也不重写留痕文件**（早前它会无条件重写 `math_11-07_legacy-mark.provenance.txt`，把「逐份明细」清空——已修，并按原文还原该文件）。
- 通用写法：`write_if_changed(path, text)`（比 `path.read_bytes()`，一致返回 False）。

> 实例：`daily\math\g9\math_g9_first_20261108.json` 的 mtime 停在 22:04，但 sha 与导入当刻完全相同——内容一字未改地被重写了一遍，只有 mtime 变了。这类「无谓 touch」会让以后的审计误判，不要再做。

#### 3.8.6 整册入库 `ops.cmd -Action import-books`（2026-11-09 新增，整册专用）

`-Action import -Date` 只扫 `daily` 目录树里的 `*_<date>.json`，整册文件在 `daily_consolidated`
另一棵树、文件名是 `*_book.json`，**永远导不到**。整册走独立 Action：

```powershell
# 只校验 + 备份 + 试跑（不写库；仍会新建一份备份快照，非纯只读）
& $Ops -Action import-books-dry -Stamp $Date -ConfirmToken I_KNOW

# 正式入库（先校验整册 → 备份 → 试跑 → 导入 → 逐册核对 → import_report_books_*.json）
& $Ops -Action import-books -Stamp $Date -ConfirmToken I_KNOW
```

按批次隔离的定向示例（2026-11-10 评审 P1-3；校验范围与导入范围取同一个文件集合）：

```powershell
& $Ops -Action import-books-dry -Stamp $Date -Grades 1,8 -ConfirmToken I_KNOW
& $Ops -Action import-books     -Stamp $Date -Subjects math,chinese -Grades 7,9 -ConfirmToken I_KNOW
& $Ops -Action import-books-dry -Stamp $Date -Only "math/g1/math_g1_first_20261109_book.json" -ConfirmToken I_KNOW
```

- `-Stamp` 不传则导 `daily_consolidated` 下**全部** `*_book.json`；传了就只导 `*_<Stamp>_book.json`。隔离件后缀是 `.quarantined.json`，不会被匹配。
- `-Subjects` / `-Grades` / `-Only`（**2026-11-10 新增**）：`db_ops.py import-books` 的 `--subjects`/`--grades`/`--only` 透传；`--only` 支持相对路径、文件名或 fnmatch 通配，逗号分隔。**校验与导入严格作用于同一批文件**，不再「全目录校验 + 按 stamp 导入」，任一坏册不再把整批（含合格册）锁死。
- 内置顺序：整册校验（非 0 即中止且**不建备份**）→ 备份 → `import_content --dry-run` → 带 `--manifest` 正式导入 → 逐册题干核对 → 报告 `import_report_books_*.json`。
- 校验失败时控制台列出**具体失败文件 + 错误数**（P1-4），机读汇总落 `books_validation_<stamp>_<时间>.json`（P0-2）。
- 报告新增 `per_book` / `per_book_summary`（**2026-11-10 复评 §八-4**）：逐册的「章节/知识点/题目 +N、跳过重复 N、manifest 跳过、导入失败原因」全部可查；`-dry` 也会写一份 `import_report_books_<时间>_dry.json`。控制台只打汇总，不再截末 8 行导致「某册到底 +0 还是被跳过」看不到。
- 幂等：同一 `-Stamp` 重跑会命中 manifest，输出「已导入且文件未变，跳过」，全表增量 0。
- 会话里由助手代跑时加 `-Unattended`（跳过运行时 6 位确认码），**其余闸门不变**；用户没在本轮明确授权写库时不要加。
- **入库前必须先过 §3.8.7 的 P3 验收闸门**。
- 实测（2026-11-09，知识点清理前）：`-Action import-books -Stamp 20261109` → 12 册、校验 12/12、试跑 EXIT=0、
  正式导入全跳过、`textbooks 146 / chapters 618 / knowledge_points 1120 / questions 2434` 前后不变、

| 2 | 单册预检 | `-Action import-books-dry -Stamp $Stamp -Only "<文件名>" -ConfirmToken I_KNOW` | `EXIT=0`，逐册 `ok 1/1` |
| 3 | 单册正式 | `-Action import-books -Stamp $Stamp -Only "<文件名>" -ConfirmToken I_KNOW` | `EXIT=0`、`[完成] 整册题目全部可查=True` |
| 4 | 试点验收 | 见下方「单册验收六项」 | 六项全过才继续 |
| 5 | 其余册落位 | 按 `subject\gN` 结构复制，已存在的跳过 | 目录内 `*_$Stamp_book.json` 数 = 计划册数 |
| 6 | 整批预检 | `-Action import-books-dry -Stamp $Stamp -ConfirmToken I_KNOW` | 校验 `全部通过`、试跑 `EXIT=0`；试跑 `questions_skipped` 应等于试点册题数 |
| 7 | 整批正式 | `-Action import-books -Stamp $Stamp -ConfirmToken I_KNOW` | `EXIT=0`、`failed=0`、`all_book_stems_in_db=True` |
| 8 | 落库后全库验收 | 见下方「全库验收八项」 | 八项全过才算交付 |

**单册验收六项**（试点册必做，任一不过就停，先修数据别往前推）

1. 该册（subject+grade+semester）题数 ≥ 文件题数，且差额只能来自同章旧题；
2. 该册同 (subject, grade) 同名多知识点 = 0；
3. `questions.knowledge_point_id` 为空的题 = 0；
4. 逐章题数可解释（基准 18 题/章，含旧题或补主观题的章会多）；
5. 抽 5 条题干（`json_extract(content,'$.stem')`）全部在库；
6. `status` 全 `published`、题-章外键违规 0。

**全库验收八项**（每次整批入库后必做）

1. 逐册把文件题干拿到库里核对：**每册 hits == 文件题数**，且报告里 `all_book_stems_in_db=True`；
2. 空挂知识点 0、题-章外键违规 0、`answer` 空值 0、`status` 全 `published`；
3. 同章同题型重复题干 0；全库跨章重复 0；
4. 同 `(subject, grade, name)` 的多知识点 **0**（不为 0 先查是不是本次引入，是就先归并，别继续导）；
5. 0 题章只允许出现在**尚未生产的年级/册**：判「本次覆盖的册」用 `where t.semester='first' and t.grade in (…)`，**不要直接数全库**（全库含下册与高中旧册，永远是几百个）；
6. 单章题量封顶可解释（本次实测上限 42，旧题共存章尤其要看）；
7. 校验器与闸门对**整个目录**复跑一遍：`_validate_daily.py daily_consolidated`、`_check_book_gate.py daily_consolidated` 全绿（隔离件后缀 `.quarantined.json` 自动跳过）；
8. 备份与报告齐备：报告 `import_report_books_*.json` 里 `per_book` / `stats_delta` / `pending_verification` 可直接抽查。

**看结果以报告为准，不看控制台**：`db_ops.py` 的整册校验仍只打 `splitlines()[-8:]`（**未修，已知债**），册数一多控制台必然截断，逐册到底 +0 还是被 manifest 跳过只能读报告的 `per_book`，别拿控制台末 8 行下结论。

**`-Unattended` 的准入条件**：只在「用户在本轮明确说了授权写库（如"执行吧""授权给你"）」时加；教研生成会话永远不加；加了也仍会先建备份，另两道闸门（`-ConfirmToken I_KNOW`、显式 `-Stamp`）不变。

**回退点要两个，不是一个**：试点前一份、整批前一份（2026-11-11 分别是 `ailearning-backup-20261111-024557.db` 与 `…-024633.db`）。整批出问题时先回整批前那份，保试点成果；全盘质疑才回试点前那份。

**知识点层四条治理规则（写库/生成都要守，2026-11-11 起生效）**

1. **`(subject, grade, name)` 必须唯一**：`import_content` 解析知识点时若同年级同名命中多个会直接 `ValueError` 中止整册。导入前先查同名，有冲突先归并再导。
2. **point 不许悬空**：`node_type='point'` 的 `parent_id` 必须非空（挂在某个 section 下）。`section` 允许是根级（全库 556 个 section **全部**根级，这是设计，不是缺陷）。
3. **section 与 point 同名时的归并规则（照这个做，别删挂题节点）**：保留 section 作为父节点，把 point 挂到它下面并改名为「原name（要点）」（库内既有命名约定，已有 40+ 个「（要点）」节点）。**禁止**为了消重删掉带题的节点，也**禁止**把挂题的 point 改成 section。
4. **禁止生成「样章·…」演示节点**：11-07 遗留的 55 组（55 section + 110 point，0 题）已于 11-11 整棵删除，`.quarantined` / 模板里再带这种分组要当缺陷处理而不是照收。

**知识点层清理的留痕要求**（照 §3.1）：改前备份 → 逐 id 清单（section/point 各列 id、name、subject、grade）→ 删前后四表计数 → 回滚命令，一起写进 `db_op_<语义>_<日期>.json`。11-11 的两份：`db_op_placeholder_kp_20261111.json`（删 165 个样章节点）、`入库执行记录_20261111.md`（含 g8 归并前后值）。

## 6. 目标库与真机验证（最容易踩的坑）

**App 不需要重构、不需要重新打包**：Flutter 客户端没有内置题库，知识点/章节/题目全部走 HTTP 实时拉取（`app\lib\core\constants\app_constants.dart` 的 `API_BASE_URL`）。只有 API **地址**变更或后端换 PostgreSQL 才需要改构建参数。

但「导入成功」≠「真机能看到」，必须确认后端进程读的是哪个库：

- **`dev` 与 `device` 是两份独立库**：`docs\content-templates\README.md` 明确真机联调常用 `ailearning_device.db`，且各有专用 manifest（`_import-manifest.json` / `_import-manifest-device.json`）。

## 8. 为什么可以反复调用

- **同日重跑**：`all-plan` 每次重算，当天文件已存在且自检通过 → `done/skip`；不重写、不加 `_r2`、不重复出题；只补 `missing`、修 `repair`。
- **入库重跑**：manifest 相同 hash + `status=ok` 自动跳过，全表增量 0；每次仍会先备份（多一份快照，无副作用）。
- **整册重跑**：`_consolidate_daily.py --apply` 同一天重跑覆盖同名 `*_book.json`（不加 `_r2`）；`import-books` 命中 manifest 输出「已导入且文件未变，跳过」，实测 `audit` diff 全 0。
- **分片 → 整册可重复**：分片本身永远进不了 manifest，但只要每次都跑一次归集，分片内容就随整册入库；改动过的整册文件因 sha 变化会被重新导入（同题干幂等跳过，不重复建题）。
- **断点续做**：46 个年级分批跑完，已完成年级已逐年级落盘，下次原样重跑同一命令接着做。
- **换日不卡同一节**：`progress_of()` 按大纲顺序 + 历史 JSON 的 section/chapters 名算 `next_section`，今天只做这一节；每次 `commit` 把真实 section 与具体下一节写进台账/日志；同一节连续 ≥2 天会提醒标注或推进；全册覆盖完进入第二轮或零新增。补漏班不推进新节。
